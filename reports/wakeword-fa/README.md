# 렌디 호출어 오인식 개선: 2단계(고립 발화) 검증

측정일 2026-11-11.
호출어 "렌디", grammar `["렌디","<UNK>"]`, 1단계 수락 규칙, Vosk lite 모델, Pleos STT/TTS, Gemini, DB는 그대로 두었다.
1단계를 통과한 후보에만 2단계 검증을 추가했다.

## 1. 결론

| 지표 (기기, 실제 앱 인식 경로) | 기존(1단계) | 적용(1+2단계) |
|---|---|---|
| 실제 한국어 연속 음성 오인식 (FLEURS ko_kr 2.11시간, 상시 대기와 같은 연속 스트림) | **154.7회/시간** | **10.4회/시간 (−93%)** |
| 단독 발화 "렌디" 검출 (합성 100개, clean/20/10/5 dB) | 80 (24/23/20/13) | 78 (24/23/19/12) |
| 유사어 단독 발화 오인식 (합성 240개, 렌트·엔디·캔디 등 주로 유사어) | 174 | 158 |
| 렌디 직전 실제 발화와의 공백 0.8 s / 1.2 s (clean, 25개 중) | 14 / 21 | 14 / 21 (변화 없음) |
| 렌디 직전 공백 0.1~0.5 s (clean) | 10~12 | 0 (의도된 제외) |
| 2단계 계산 시간 (후보당) | – | 중앙값 0.10 ms, p95 0.48 ms, 최대 5.3 ms |

- 반복성: 같은 기기에서 측정을 반복했을 때 기존 방식은 150.5~154.7회/시간, 0.45 s 설정은 12.3~16.1회/시간이었다.
- 응답 지연: 2단계는 Vosk가 구간 끝(0.65 s 무음)을 판정할 때 이미 버퍼에 있는 오디오만 쓴다. 추가 대기가 없고 계산은 1 ms 미만이다. 호출 감지 → "네, 말씀하세요!" 경로는 바뀌지 않았다.
- 남은 한계
  - 렌디와 비슷한 유사어를 단독으로 말하는 경우는 거의 줄지 않는다(174 → 158). 이건 음향 모델이 구분해야 하는 문제다.
  - 남은 10회/시간은 앞뒤에 쉼이 있는 1.1~1.5 s 길이의 짧은 구절이다(예: 낭독 시작 직후 첫 단어).
  - 합성 렌디 1개 목소리와 낭독 음성 기준이므로 실차 수치는 `TEST_PLAN.md`로 다시 측정해야 한다.

## 2. 기존 방식 분석 (`RendyWakeWordController.kt`)

- **인식기**: grammar `["렌디","<UNK>"]`, `setWords(true)`, `setEndpointerDelays(5.0, 0.65, 8.0)`.
  발화가 끝나고 0.65 s 무음이면 구간 결과가 나오고, 최대 구간 길이는 8 s다.
- **수락**: 구간 결과 텍스트에서 공백을 지운 값이 정확히 "렌디"이고 최소 단어 confidence가 0.70 이상이면 수락한다. partial 결과는 로그에만 남긴다.
- **RMS**: 타이밍 로그에만 쓰고 수락 판정에는 쓰지 않는다.
- **원인**
  - 후보가 두 단어뿐이라, 짧은 구절은 대부분 confidence 1.0의 "렌디"로 강제 정렬된다.
  - `<UNK>`가 이를 흡수하지 못한다. 실제 음성 2.1시간에서 1단계만으로 154.7회/시간이 나왔다.
  - confidence는 거의 항상 1.0이라 임계값을 조정해도 소용이 없다.

## 3. 2단계 후보 비교 (효과를 가정하지 않고 측정)

호스트 탐색은 Python Vosk 0.3.45로 했다. 이 버전은 끝점 설정 API가 없어 근사치다.
최종 판단은 기기 측정으로 했다. 표의 FLEURS FA/h는 호스트 기준 121회/시간에서 출발한다.

| 방법 | 검출(합성 100) | 실제 음성 FA/h | 판정 |
|---|---|---|---|
| 1단계만 | 79 | 121.0 | 기준 |
| 렌디 단어 길이 ≤ 1.0 s | 71 | 107.7 | 효과 작음 |
| 앞 0.5 s 에너지 비율 < 0.5 (절대 에너지) | 71 | 27.1 | 잡음 환경에서 검출 손실 |
| 유사어 grammar(92단어) 재디코딩 첫 단어 = 렌디 | 44 | 0.0 | 검출 손실이 너무 큼 |
| 전체 LM 자유 인식 음절 수 ≤ 3 | 77 | 53.2 | 전체 LM이 필요해 메모리 +84 MB |
| N-best 점수 차 | – | – | 대안 경로가 거의 나오지 않아 쓸 수 없음 |
| **배경 대비 고립 발화 검사**(유성 구간 ≤ 1.5 s, 앞뒤 창 내 음성 < 60 ms) | 77 | 15 (0.45 s 창) / 6 (0.6 s 창) | **채택** |
| sherpa-onnx open-vocabulary KWS + 한국어 Zipformer (전용 엔진 대안, 아래 4장) | 22~37 | 0.0 | 검출률이 너무 낮음 |

### 기기에서 고른 최종 설정 (같은 실행에서 동시 비교, `device/metrics_final.txt`)

| 설정 (배수/창/허용/최대구간) | 단독 렌디 | 유사어 | 실제 음성 FA/h | 공백 0.5 s 검출 |
|---|---|---|---|---|
| 1단계 | 80 | 174 | 154.7 | 11 |
| 2.0 / 0.6 s / 60 ms / 1.5 s **(채택)** | **78** | 158 | **10.4** | 0 |
| 2.0 / 0.6 s / 60 ms / 1.2 s | 70 | 158 | 4.3 | 0 |
| 2.0 / 0.75 s / 60 ms / 1.5 s | 73 | 148 | 8.1 | 0 |
| 2.0 / 0.6 s / 40 ms / 1.5 s | 68 | 129 | 8.5 | 0 |
| 3.0 / 0.6 s / 60 ms / 1.5 s | 77 | 161 | 18.0 | 5 |
| 2.0 / 0.45 s / 60 ms / 1.5 s (직전 실행) | 77 | 160 | 16.1 | 11 |

선택 기준은 사용자 지시에 따랐다. 일반 대화 직후 0.1~0.3 s 안의 호출은 최적화 대상에서 제외하고, 단독 렌디 검출률을 유지하는 설정 중 오인식이 가장 적은 것을 골랐다.
더 엄격한 설정(최대구간 1.2 s, 창 0.75 s, 허용 40 ms)은 오인식이 더 적지만 단독 렌디 검출이 5~12개 떨어져 제외했다.

## 4. 전용 wake-word 엔진 비교 (Android 오프라인)

| 엔진 | 한국어 "렌디" | 라이선스 | 메모리·CPU | 모델 학습 | 측정 결과 |
|---|---|---|---|---|---|
| Vosk(현재) + 2단계 | grammar로 바로 가능 | Apache-2.0, 모델 Apache-2.0 | 기기 PSS 약 411 MB(lite) | 불필요 | 위 표 |
| sherpa-onnx KWS | 한국어 KWS 모델 없음. 한국어 ASR(Zipformer)을 open-vocabulary로 사용 | 코드 Apache-2.0. 모델은 KsponSpeech(AI Hub) 학습 → 이용 조건 확인 필요 | int8 인코더 121 MB + 디코더/조이너 14 MB. 호스트 RTF 0.14 | 불필요 | 검출 22~37/100, 유사어 0~1/240, 실제 음성 0회/2.1시간 → 검출률 부족 |
| Porcupine (Picovoice) | 한국어 지원, Console에서 사용자 호출어 생성(.ppn) | 상용. AccessKey 필요. 무료 티어는 2026-06-30 종료로 보도됨 → 상용 계약 필요 | 공급사 자료상 수 MB, 저전력 (미측정) | Console에서 생성(데이터 불필요) | 라이선스 없이 측정 불가 |
| openWakeWord | 영어 중심. 한국어는 직접 학습 필요 | 코드 Apache-2.0. 공식 사전학습 모델은 CC BY-NC-SA 4.0(상업 사용 불가) | 수백 KB~수 MB, ONNX/TFLite | 필요: 한국어 TTS 합성 + 실제 음성 부정 샘플. 학습 데이터 라이선스 확인 필요 | 미측정 |
| microWakeWord | 영어 중심 | Apache-2.0 (학습 데이터 라이선스 별도) | INT8 TFLite, 수십~수백 KB | 필요 | 미측정 |

- 결론: 지금 바로 정확도와 라이선스를 모두 만족하는 전용 엔진은 확인되지 않았다.
  - Porcupine은 상용 계약이 전제다.
  - openWakeWord와 microWakeWord는 한국어 "렌디" 학습 데이터(실제 화자 + 차량 소음)가 있어야 비교할 수 있다.
- 그래서 이번에는 Vosk를 유지하고 2단계 검증만 추가했다. 전용 엔진 전환 여부는 `TEST_PLAN.md`의 실화자·실차 데이터로 판단한다.

## 5. 구현 (미커밋)

- `service/RendyWakeIsolationCheck.kt` (신규)
  - 20 ms 프레임 RMS 링버퍼(`FrameEnergyTracker`, 12 s). 인식기와 같은 바이트를 넣어 Vosk 단어 시각과 맞춘다.
  - 고립 판정: 배경(p20) × 2.0 초과를 유성으로 보고, 120 ms 이하 틈은 이어 붙인다. 유성 구간 ≤ 1.5 s이고 앞뒤 0.6 s 창 안의 음성이 각각 60 ms 미만이어야 통과한다.
  - Vosk 단어 시각이 아니라 실제 유성 구간 기준이라, 느리게 말한 "렌-디"가 잘리지 않는다.
- `RendyWakeWordController.kt`
  - `createRecognizer()`(실사용과 self-test 공용), `decide()`에 단어 시각 추가, `verifyIsolation()`.
  - 1단계 수락 후 2단계에서 탈락하면 `Wake word rejected: reason=not_isolated (...)` 로그를 남기고 계속 대기한다.
  - 빌드 플래그 `-Prendy.wakeword.isolation=false`로 끌 수 있다. 디버그 빌드는 `debug.rendy.wake.isolation=on|off`로 바꿀 수 있다.
- `RendyWakeWordSelfTest.kt`
  - 실제 인식기 설정을 쓰고, 연속 스트림 세트(`*_stream`)를 지원한다.
  - 2단계 후보 설정 6개를 같은 활성화에 동시에 평가하고, 평가 시간을 기록한다.
- `app/build.gradle.kts`: `RENDY_WAKE_ISOLATION` (기본 true)
- 테스트: `RendyWakeIsolationCheckTest` (신규 9개). 전체 단위 테스트 94개 통과, 2개 skip.
- 확인 범위
  - 에뮬레이터 마이크는 무음이라 실시간 마이크 경로의 2단계 동작은 기기에서 소리로 확인하지 못했다.
  - 같은 코드(`decide`, `FrameEnergyTracker`, `evaluate`)를 쓰는 self-test와 단위 테스트로만 확인했다.
  - 실시간 대기는 정상 시작된다(`Wake-word microphone is capture-ready`).
