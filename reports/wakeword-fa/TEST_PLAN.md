# 렌디 호출어 실사용 평가 계획 (실제 화자 + 차량 소음)

현재 수치는 다음 두 종류의 데이터로만 측정했다.
- 합성 음성: Windows TTS Heami 1개 목소리로 만든 340개 회귀 세트.
- 실제 화자 낭독 음성: FLEURS ko_kr 2.1시간. 차량 소음은 들어 있지 않다.

실차 적용 전에 아래 데이터를 만들어 같은 도구로 다시 측정한다.

## 1. 측정 도구 (이미 구현됨)

- **기기 측정**: 디버그 빌드의 `ACTION_WAKEWORD_SELFTEST`
  - 실제 앱 경로를 그대로 쓴다: `createRecognizer`(grammar, 단어 시각, 끝점 0.65 s), 2048 B 청크, 1단계 `decide`, 2단계 `RendyWakeIsolationCheck`.
  - `files/wakeeval/<세트>/`: 파일마다 새 인식기를 쓴다. 검출률 측정용이다.
  - `files/wakeeval/<세트>_stream/`: 모든 파일을 하나의 연속 스트림으로 처리한다. 상시 대기와 같은 조건이며, 시간당 오인식 측정용이다.
  - 결과 `result_lite.json`에는 활성화마다 2단계 후보 설정별 판정과 평가 시간이 들어 있다.
- **집계**: `tools/device_metrics.py <result.json> <posctx_meta.json>`
- **입력 형식**: 16 kHz mono 16-bit WAV. 다른 형식은 `tools/fleurs_convert.py`와 같은 방식으로 변환한다.

## 2. 데이터셋

| ID | 내용 | 규모(최소) | 용도 |
|---|---|---|---|
| R1 실화자 렌디 | 화자 20명 이상(성별, 연령 20~60대, 사투리 포함). 각자 "렌디"를 평소·빠르게·작게·크게·부르듯이 길게 등 10회. 문장 앞에서 "렌디 … 라이트 켜줘"처럼 끊어 말하기 포함 | 200회 이상 | 검출률 |
| R2 차량 소음 | 정차(공회전), 시내 30~50 km/h, 고속 80~110 km/h, 공조 최대, 창문 개방, 빗길, 음악 재생 중. 각 10분 이상, 운전석 마이크 위치 | 70분 이상 | R1, R3와 합성, 소음 단독 오인식 |
| R3 차내 대화 | 운전자·동승자 일상 대화, 전화 통화(한쪽), 라디오 및 팟캐스트 음성, 내비 안내음 | 3시간 이상 | 시간당 오인식(주 지표) |
| R4 유사어 | "렌트, 렌즈, 엔디, 레디, 캔디, 핸디, 펜디, 웬디, 렌터카, 랜드" 등을 문장 속에서, 그리고 단독으로 | 화자 10명 × 20개 | 유사어 오인식 |
| S 회귀 | 기존 합성 340개(`device_audio`) + 발화 뒤 렌디 300개(`posctx`) + FLEURS 2.1시간 | 고정 | 코드 변경마다 회귀 확인 |

- R1, R4는 실제 차량 마이크로 녹음하는 것이 가장 좋다. 불가능하면 정숙한 방에서 녹음한 뒤 R2와 SNR 20/10/5/0 dB로 합성한다.
- R1은 각 녹음 앞에 2초 이상의 침묵이나 차량 소음을 두고, 직전 발화와의 간격을 0.5/0.8/1.2 s 이상으로 나눠 녹음한다.
- 개인정보: 화자 동의서를 받고, 원본은 내부 저장소에만 보관하며 학습에 쓸지 별도로 동의를 받는다.

## 3. 지표와 합격 기준(안)

| 지표 | 정의 | 기준(안) |
|---|---|---|
| 검출률 | R1(조용함, 소음별)에서 렌디 발화 중 활성화된 비율 | 조용함 ≥ 95%, 시내 소음 ≥ 90%, 고속 ≥ 80%. 2단계 적용 전후 차이 ≤ 2%p |
| 시간당 오인식(FA/h) | R3 연속 스트림 활성화 수 ÷ 시간 | 주행 대화 ≤ 1회/시간 (단기 목표 ≤ 5회/시간) |
| 소음 단독 오인식 | R2만 연속 스트림 | 0회/시간 목표 |
| 유사어 오인식 | R4 단독 발화 중 활성화 비율 | 보고. 현재 구조로는 높을 것으로 예상 |
| 응답 지연 | 렌디 발화 끝 → 응답 TTS 시작 | 2단계 적용 전후 차이 ≤ 20 ms (2단계 평가 시간 별도 보고) |

## 4. 절차

1. R1, R2, R3, R4를 16 kHz WAV로 정리한다. 파일명에 화자, 조건, SNR, 간격을 넣는다(예: `spk07_city_snr10_gap800_take3.wav`).
2. R3는 `r3_stream/`, R2 단독은 `r2noise_stream/`, R1과 R4는 일반 세트로 `adb push`한 뒤 `run-as … cp`로 `files/wakeeval/`에 복사한다(`reports/wakeword-memory/README.md` 절차 참고).
3. 앱을 재시작하고 `adb shell am start-foreground-service -n com.hyundai.rentalhelper/.service.CoachOverlayService -a com.hyundai.rentalhelper.action.WAKEWORD_SELFTEST`를 실행한다.
4. `result_lite.json`을 가져와 `device_metrics.py`로 1단계와 2단계 설정별 표를 만든다. R1은 파일 단위, R3는 시간당으로 본다.
5. 실차에서 실제 마이크로 30분씩 대화하며 확인한다. 로그 `Wake word detected`와 `Wake word rejected: reason=not_isolated`를 세어 오프라인 결과와 대조한다.
6. 2단계 파라미터(창 길이, 허용 음성 ms, 최대 구간, 음성 임계 배수)를 R1/R3 결과로 다시 고른다. 같은 데이터로 고르고 보고하지 않도록, 화자를 반으로 나눠 선택용과 검증용으로 쓴다.

## 5. 다음 단계 판단 기준

- 2단계 적용 후에도 R3 FA/h가 목표(≤ 1~5회/시간)를 넘거나 R4 유사어 오인식이 문제가 되면, Vosk grammar 방식으로는 한계가 있다.
- 그때는 전용 KWS를 R1, R2로 학습해 같은 지표로 비교한다.
  - openWakeWord나 microWakeWord 구조를 쓰되, 공식 사전학습 모델이 아니라 직접 학습한 모델이어야 한다(라이선스 문제).
  - 또는 Porcupine 상용 라이선스.
